# Worklog — v2.58.1 (in progress)

## Added

- Colour search in the Search views (catalogue), the same matching as tigersystem.io's colour finder: a colour button in the search bar (shown only there) opens a side card where a colour is set by HEX (field, 14 quick picks, the in-app picker), by RAL Classic code or name (the list shows all 215 colours, scrolling, and narrows as you type; `ral-classic.js`; the names are English, so a colour word typed in the app's language — "rouge", "vert clair", "grün", "红色" — is read through the translated word list `colorSearchRalWords`), or by clicking a photo dropped, pasted or chosen there (average of the 5×5 pixels under the pointer, photo downscaled to 1200 px, never uploaded). The 14 quick picks sit in two rows of 7, round (the swatches are buttons: `height: auto` against the global button height); the "current colour" box sits right under the mode tabs, above the RAL search and the photo, and shows in those two modes only (in HEX mode the field already shows it). A ΔE slider (1–30, default 10, with the site's band label) keeps the products within that CIEDE2000 distance (D65 Lab, alpha dropped, a multicolour product counted by its closest colour and left out unless "Include multicolour" is on or its brand declared the RAL searched for — `rals` / `ral`, empty in the catalogue today); results sorted declared RAL first, then ΔE, each hit's "ΔE x.x" shown as a badge at the bottom left of its picture while the colour search is on (the TD badge's place and look, a dot in the band's colour; on the table thumbnail too). The active colour shows as a chip of the filter bar (click to edit, ✕ to remove); the reset button and the empty state's "Clear the filters" clear it too — new `renderer/color-search.js` (`mountColorSearch`, `hexToLab`, `deltaE2000`, `ralColor`, `deltaBand`, maths ported from TigerTag_Hub `lib/colorMatch.ts`); `renderer/inventory.js` (`openColorSearch`, `closeColorSearch`, `_catColorSet`, `_catColorChipSync`, `_catColorApply`, `_catDeHTML`, hooks in `_catViewSearch`, `_anyFilterActive`, `_syncPanels`, `_closeAllSideCards`, `_clearSideForChip`, `setViewMode`); `renderer/inventory.html` (`#searchColor`, `#colorSearchPanel`); `renderer/css/70-detail-misc.css` (`.inv-search-color`, `.csr-*`, `.cv-color-chip*`, `.cv-de`); `renderer/CODEMAP.md` (ranges remapped), `CLAUDE.md` file map, `docs/i18n-keys.md`.

- One search bar with filter chips written in it, Shopify admin's pattern as Atome3D's Galaxy does it: the chips sit in the search field before the text, on one line (chips that do not fit scroll sideways in their strip; the text keeps at least 120 px; every editor opens under its chip). A click in the field, its filter icon or ↓ lists the fields under it; typing narrows that list (first row: keep the text as a search) and Enter adds the one field the text names; ↑ ↓ walk the list. Picking a field adds its chip and opens its editor (values ticked with their counts, a search when the list is long, an is / is not switch; Weight takes at least / at most in g). Chips combine with AND, the values inside a chip with OR, one chip per field; a click on a chip reopens it, its ✕ removes it, Backspace in the empty field removes the last one. Fields: spools — Brand, Material, Aspect, Type, Diameter, Tag, List (to order / favourite), Weight, Rack (or not stored); Favourites and Lists — Brand, Material, Aspect, Tag, List; catalogue (Search views) — Brand, Series, Material family, Aspect, Type, with the colour search as a chip. Every condition compares the IDs a record carries (`id_brand`, `id_material`, `id_aspect1/2`, `data1`, rack id), never a label. The counts follow the other chips and the typed text. The colour bars, when set, show as a "Colour" chip (✕ resets them). The header's TigerTag / TigerTag+ / TigerData / TigerData+ tiles set and clear the Type chip and light up with it (the TigerData tiles now in the same accent as the others — `renderer/css/00-base.css`). Chips belong to the view segment (cleared when leaving it, by the reset button, on an account or friend switch). The TigerQR link paste / scan into the field is unchanged — new `renderer/filter-bar.js` (`mountFilterBar`); `renderer/inventory.js` (`FB_FIELDS`, `_fbScope`, `_fbPass`, `_fbOptions`, `_fbFieldDefs`, `_fbExtraChips`, `_fbSetConds`, `_fbSyncTiles`, `_prodIds`, `_catBrandKey`, `_prodTextPass`, `state.filters`, row `brandId` / `materialId` / `diameterId` in `normalizeRow`; `applyInventoryFilter`, `applyRackSearchDim`, `filteredRows`, `_filteredProducts`, `_catViewSearch`, `_clearSearchFilters`, `_anyFilterActive`, `_catColorChipSync`, stat tile click); `renderer/inventory.html` (`#fbBar` inside `.inv-search`, filter icon `#fbAddBtn`); `renderer/css/70-detail-misc.css` (`.inv-search` is now the pill box holding chips and text, `.fb-*`, `.inv-search-filter`), `renderer/css/40-printers.css`; `renderer/CODEMAP.md`, `CLAUDE.md` file map, `docs/i18n-keys.md`.

## Changed

## Fixed

- A product whose photo changed in the catalogue no longer keeps its old picture on the spool thumbnails: a spool whose image address carries a lower version (`img?id=…&v=N`) than the catalogue's counts as behind (`_imgVersion`, `_catalogStaleRows`); the catalogue copy is checked at launch and when the window comes back, every 6 hours instead of once a day and only from the catalogue views (`CATALOG_TTL_MS`, `_catalogAutoSync`); opening a spool asks the product API once a session and rewrites the spool only when the product is ahead (`_catalogCheckOnOpen`, `_refreshApiData` `ifNewer`), with one retry 2 s later (the API answers 503 now and then); the automatic refresh, run on every server snapshot of the inventory, asks for one spool at most every 30 minutes, so a spool still counted behind after its refresh is not asked and written in a loop (`CATALOG_RETRY_MS`, `_catalogRefreshedAt`, `_catalogRefreshStale`) — `renderer/inventory.js`.
- "Link the proprietary Tags" is offered only for the brands that ship chips of their own — Bambu Lab, Snapmaker, ELEGOO, Anycubic, Creality, QIDI Tech, Prusament, by `id_brand` (`MAKER_CHIP_BRANDS`, `brandHasMakerChips`, `renderer/rfid_protocol/linked/index.js`): the spool card banner, the product card, the add-product foot (re-drawn on a brand pick) and the link grid; an R3D spool shows its burn banner instead.

- A spool flagged "Please update your TigerTag+" (`needUpdateAt`) whose chip could not be rewritten on the TigerPOD (lifted too soon, update window open, write not verified) no longer has its record overwritten with the chip's old values: the record is kept (only a twin link seen beside it is written) and the chip is rewritten on its next presentation. A spool the catalogue has moved on from is reconciled from the catalogue as soon as its chip is read (`_catalogStaleRows` → `_refreshApiData`), then its chip rewritten in the same pass — `renderer/inventory.js` (`_processNfcScans`).

- Chip backups (`users/{uid}/rfidList/{UID}.backup`) are stored for TigerTag+ Certified chips only (signature verified in main, `tagData._certified`): a plain TigerTag / TigerTag+ only has its UID listed — `recordRfidChipScan`, `renderer/inventory.js`. A `.ttag` restore no longer overwrites a chip entry already on the account and writes a missing one with the client-writable fields only (`firstSeenAt`, `lastSeenAt`, `seenCount`, `backup`). Comments: rfidList header in `renderer/inventory.js`, `renderer/rfid_protocol/restore/index.js`; `docs/firestore-schema.md` rfidList section. Backend (TigerTag_Firebase_Backend f06ed78, deployed 2026-11-17): `firestore.rules` rfidList — no delete, backup write-once, client keys `hasOnly`; `certifyChip` stamps `certified` / `certifiedAt` on a verified backup and removes one that does not verify; README. One-off admin function `cleanChipBackups` (dry run by default) deployed and run on 2026-11-17: 2,247 non-certified backups removed on 193 accounts, 1,673 `rfidBackup` markers reset, 1,353 Certified stamped; a re-count finds 1,353 backups, all Certified. The function was then deleted from Firebase and its code removed (backend 47d44b2, 2026-11-17).

- A catalogue update now reaches both chips of a twin spool: `_refreshApiData` writes the same update to the twin's doc in one batch (the pair split, one chip at 230 °C, the other at 240). The TigerPOD's automatic chip rewrite clears `needUpdateAt` only if it is still the value it wrote from (transaction); a record that moved on during the write stays flagged for the next presentation — `_autoUpdateChip`, `renderer/inventory.js`.
- A TigerTag whose pages could not be read (the spool moved during the read) no longer passes for a maker's chip and opens the new-chip card: an NTAG (PC/SC card name 0003 in the ATR) read without pages is ignored until the next read — `main.js` (`card` message handler).
