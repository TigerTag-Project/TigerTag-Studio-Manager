# Worklog — v2.62.0 (in progress)

## Added
- Labels: print a label on a Bluetooth label printer from the label card ("Bluetooth label printer" button, under Print): Niimbot (B1, B1 Pro, B21, B21 Pro, B3S, B18, D11, D101, D110, D110_M), Phomemo M110 / M120 / M200 / M220 / M221 and Marklife P15, model by model as the mobile app does (`renderer/labels/ble-printer.js`, Web Bluetooth). The model comes from the Bluetooth name; the label is built at the printer's resolution (300 dpi on the B1 / B21 Pro) and the narrow 12 mm heads (D-series, B18, P15) always print the slim 40 × 12 template turned a quarter. Every Bluetooth print keeps a safety margin on each side of the label, on both axes (0.5 mm), on top of the template's (the drawing is scaled down and centred; PNG / PDF / SVG unchanged). Niimbot speaks one of three sequences; the D110_M asks its protocol (from 300: the v4 sequence, the only one that inks it). Each printer keeps the template of its roll (keyed by its Bluetooth name, `tigertag.blePrinter`): a print takes the printer's own, else the template picked last, and the card switches to it; picking a template stores it for the printer used last. Several printers in range are listed under the button to pick one (`select-bluetooth-device` in `main.js`, `ble:prefer` / `ble:choose` / `ble:cancel` / `ble:devices` / `ble:gave-up`, bridged in `preload.js`); one in range is taken at once. Checked on paper from Studio: D110_M (slim 40 × 12), B1 (classic 40 × 30, centred). macOS: `NSBluetoothAlwaysUsageDescription` in `package.json` `build.mac.extendInfo`. Files: `renderer/labels/ble-printer.js`, `renderer/labels/index.js`, `renderer/labels/labels.css`, `main.js`, `preload.js`, `package.json`, `docs/i18n-keys.md`.
- Labels in a batch: in select mode, the bulk bar's "Labels" (own inventory only) opens the label card on the selected spools — "N labels" with the preview browsed one by one, one template and the same values for all, the Spool / Filament switch making it one label per spool or one per filament (spools of one catalogue product share one; a spool with no product keeps its own). "Print N labels on <model>" sends them in one go to the default Bluetooth label printer: Niimbot b1 / v4 as ONE connection and ONE job of N pages (count in print start, each page sized / sent / ended, then the status until N are out), the old Niimbot form repeating its one-page job on one connection, the Marklife P15 one connection per label with the LOW speed and a medium density (one job per connection only), Phomemo one connection per label — as validated on paper from the Mac on the B1, B1 Pro, D110_M and P15 (2026-11-26). While it runs the key becomes Stop and the message says "Label 3 / 12…"; stopped or dropped, it says how far it got and "Resume from label N" goes on from the next one. Every label printed counts as a print (print_label). A batch is Bluetooth only (the card says so; PDF / PNG / SVG stay on a single spool's label). `printLabelsBle` (one label = a batch of one), `niimbotRun`, `phomemoOne`, `marklifeOne` (`ble-printer.js`), `openLabelBatch`, `batchItems`, `printBatch` (`labels/index.js`), `#bulkLabels`. i18n: `bulkLabels`, `labelBatchCount`, `labelBlePrintN`, `labelBatchPrint`, `labelBatchStop`, `labelBatchProgress`, `labelBatchResume`, `labelBatchStopped`, `labelBatchDone`, `labelBatchFailed`, `labelBatchBleOnly`. Files: `renderer/labels/ble-printer.js`, `renderer/labels/index.js`, `renderer/labels/labels.css`, `renderer/inventory.js`, `renderer/inventory.html`, `renderer/css/70-detail-misc.css`, `renderer/CODEMAP.md`, `renderer/locales/*.json`, `docs/i18n-keys.md`.
- Bambu Lab P3C: catalogue id 15 (`data/printers/bbl_printer_models.json`, picture `assets/img/bbl_printers/p3c.png` cut out of Bambu Lab's store photo), model code `N11` and serial prefix `331` in `probe.js` (plus the H3C's `32X` → 14), both read off Bambu Studio's `resources/printers/N11.json` / `N10.json`. The H3C with seven PrintTools instead of nine: the same tool reading gives seven pills T1–T7; its AMS 3P (module `n11a`) is a new unit kind `ams3p` with seven bays ("AMS 3P", 4 + 3 on the board, 5 + 2 on the Filament card) and, like the H3C, no external spool tile unless the machine reports one (`bambuHasExt`, `bambuBayCount` in `cards.js`, `_bblParseModules` in `index.js`, `_UNIT_WORD` in `inventory.js`). The chamber is shown without a setpoint: Bambu Studio has `support_chamber_temp_edit` false for it. Never seen on a real P3C — assumed to report like the H3C. Docs: `renderer/printers/bambulab/PROTOCOL.md` §16.10 + appendix A, `docs/printer-storage-terms.md` (`ams3p`).

## Fixed
- Bambu Lab RTSP cameras (X1C / X1E / P2S / H2x): the live view no longer repeats one picture for seconds. Pictures dated on arrival (since 2.46) went through an `fps=30` filter: a burst arriving together fell into one 1/30 s slot, the rest was dropped and the one kept repeated until the next burst (an X1C measured at 468 pictures in 15 s, 61 different, one held 3.5 s). The filter is gone and `-fps_mode vfr` sends each decoded picture once (not `passthrough`: two pictures with the same arrival date stopped ffmpeg, "Invalid pts <= last"). Measured on that X1C after a reboot: 585 pictures in 64 s, all different, longest gap 1.4 s. What remains is a TLS cut (`-9806`) about once a minute, from the printer side, after which the feed restarts. Files: `main.js`, `CODEMAP-main.md`.
- Bambu Lab cameras no longer stay frozen for good. The RTSP restart count never went back to zero, so those once-a-minute TLS cuts used up the 10 restarts and the camera gave up after ten minutes or so of a healthy stream; the count now restarts with each launch that delivers a picture (the JPEG cameras already did). And a camera that has stopped (given up while a printer rebooted, say) is started again when the camera wall or the printer card is reopened: it counts as running only while pictures arrive (`_camRunning`, 20 s), no longer as soon as a last picture is kept. Files: `main.js`, `renderer/printers/bambulab/index.js`.
- Snapmaker: the Moonraker link opens with the account, like Bambu Lab, Elegoo and Anycubic, instead of only when a Printers view or the side card is shown, so the MCP `list_printers` reads the job and the loaded filament of a U1 that is printing (#366, by Ptitlouis6012; checked on the demo U1, not on a real one). Files: `renderer/inventory.js`, `renderer/CODEMAP.md`.
- TigerCoins: the Deals banner's balance now follows a send. Sending coins (or any fresh status) updated the header balance but not the banner card, which kept the figure of its last render until the view was redrawn; `_paintDealsBadge` now patches the banner's balance and its accessible name in place. File: `renderer/inventory.js`.
- Cart: adding a product the stock already covers now lists it (explicit quantity 1, `orderQty`), and the cart button on a product marked earlier but hidden does the same, then opens the cart (#365, by Ptitlouis6012). Files: `renderer/inventory.js`, `renderer/CODEMAP.md`.
- RFID readers on Windows: the "Microsoft IFD" reader Windows lists on its own (seen on a Surface Go 2 next to a TigerPOD, never holds a chip) is skipped like the YubiKey / Windows Hello / ROCKEY ones, so the burn window no longer waits on it for good (#362, by Ptitlouis6012; not tested on a Surface). File: `services/nfc-process.js`.
- Anycubic Cloud: an expired session is now said, and announced before it ends. The cloud token is a JWT good for 90 days (`exp`, read on a Kobra X token) that a newer slicer login can also revoke; when it ended, the cloud answered `10001` to everything (camera included) and Studio only showed one toast that went away — the printer looked fine and the camera stayed black. Now `acuCloudAuth` reads the token's `exp`: from 14 days before it, a warning banner tops the printer's live block (and one toast per launch in the last 7 days); once rejected (`10001`, camera order 1001 included) or past `exp`, the badge says "Session expired" and a red banner says what is lost. Every cloud REST answer goes through `_acuAuthCheck` (getInfo, printer info, orders, slot / external spool sets, files list / delete, camera order 1001), so any 10001 starts it; the camera box itself then says the session expired, with Reconnect, instead of a silent hero photo (`widget_camera.js`, `acuCloudCamExpired`). Both banners carry a Reconnect key (`acuCloudReconnect`): a bridge-mode slicer's token if one is running, else the Anycubic Cloud sign-in panel in reconnect mode (`openAcuCloudReconnect`, titled "Reconnect"), whose verified token goes to every cloud printer (`_acuApplyCloudToken` → `updateAnycubicCloudToken`). The sign-in webview now also loads when it was created a moment earlier (it waited for `dom-ready`). Files: `renderer/printers/anycubic/index.js`, `renderer/printers/anycubic/add-flow.js`, `renderer/printers/anycubic/widget_camera.js`, `renderer/printers/anycubic/anycubic.css`, `renderer/printers/anycubic/PROTOCOL.md`, `renderer/locales/*.json`, `docs/i18n-keys.md`.
- Colour search: a product's brand-declared RAL now counts. `_catRals` read top-level `rals` / `ral`, which catalogue items do not have, so "declared by the brand" never fired; it now reads `color_info.rals` / `ral` and keeps only the codes whose `ral_sources` / `ral_source` is `brand` (a RAL the Manager estimated, source `auto`, never jumps the ΔE order). Same rule as the mobile app. No bundled product carries a brand RAL yet, so nothing changes on screen today. File: `renderer/inventory.js`.
- Colour bars and colour search are one at a time, as the two bars already were: touching a bar drops the colour search (HEX / RAL / photo), and picking a colour puts the bars back. Asking for both used to intersect two unrelated searches and read as a broken filter. File: `renderer/inventory.js` (`_catColorSet`, the views' `hueGroup.solo`).
- Catalogue view emptied by the filters: the title said "It's there — your filters are hiding it", which read as nonsense; it now says "Nothing gets through these filters" (`catEmptyFilteredTitle`, 11 locales, same wording as the mobile app).
